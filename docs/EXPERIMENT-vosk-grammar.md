# 实验：能不能用 Vosk 的"语法模式"当 M1（2026-11-16）

## 动机

M1（sherpa-onnx 流式 14M）是**自由识别**，所以会输出词表外的东西：
「我说完了」被听成「播完了」、「暂停视频」被听成「淡定视频」。

[Vosk 的语法模式](https://qiita.com/yamashita_aidev/items/98cffbd5d2f558594f03) 声称能把识别范围限制到注册词表，
**词表外的东西不可能作为结果返回**。如果成立，这类错误从结构上就不存在了。

## 环境与结论摘要

| 项 | 结果 |
|---|---|
| 模型 | `vosk-model-small-cn-0.22`（zip 42MB，解压 65MB，Apache-2.0） |
| 安装 | **npm 的 `vosk` 包装不上**（依赖 ffi-napi，需要 VS 编译工具，且 Node 24 不兼容）；改用 Python wheel `pip install vosk` |
| 语法格式 | **只接受 JSON 字符串数组**，不接受 JSGF（`SetGrammar` 直接报 `Expecting array of strings`） |
| 中文要点 | **整词数组会被静默忽略**（`Ignoring word missing in vocabulary: '听我说'`）；**必须用单字数组**，输出是带空格的字序列（`听 我 说`） |

## 实测（30 段真人录音，同一批数据）

| 指标 | Vosk 字符级语法 | 14M 流式（现状 M1） | paraformer 80MB（现状 M2） |
|---|---|---|---|
| 端尾命中率 | **22/30 = 73%** | 12/30 = 40%（`matchOne` 口径 63%） | 25/30 = 83% |
| 模型加载 | **246 ms** | ~900 ms | 850 ms |
| 每段耗时 | 118 ms（整段批处理） | 实时（3–4% CPU） | 43 ms（8 线程） |
| 内存 | **+105 MB** | 120 MB | 190 MB |
| 词表外输出 | **不可能**（只能出注册字符） | 会（「播完了」「淡定视频」） | 会 |

未命中的 8 条：

```
把声音调大→空          把声音调大→「把 声 调 大」     ← 漏了「音」，0.8 相似度
把声音调小→「把 声 调 小」 把声音调小→空
播放爱奇艺→空
暂停视频→「暂 听 视 频」×2  暂停视频→空
```

注意：「把 声 调 大」这类虽然过不了端尾匹配，但**分数 0.8 会进入候选**（pipeline 的 candidateFloor=0.35），
仍会被 M2 裁决救回 —— 所以真实流水线里的表现会好于 73%。

## 重要更正：增益来自**模型**，不是语法（2026-11-16 复测）

用户质疑"语法模式会不会让每句话都映射到关键词"，这个质疑是对的。把两者拆开测：

| 模式 | 命中率 |
|---|---|
| **A 自由识别（不加语法）** | **23/30 = 77%** |
| B 字符语法（无 `[unk]`） | 22/30 = 73% |
| C 字符语法 + `[unk]` | 21/30 = 70% |

**结论：语法模式不但没有帮助，反而降了 4~7 个百分点。** 之前看到的"73%"不是语法的功劳，
而是 `vosk-model-small-cn-0.22` 这个模型本身比我们的 14M zipformer 更准（自由识别 77% vs 60%）。

语法模式的真实作用（应该这么用，而不是用来提准确率）：
- **搜索空间小 → 解码更快**（适合嵌入式/低功耗）
- 可以给 `[unk]` 一个**显式拒识类**
- 代价：不给 `[unk]` 时，**任何输入都会被强制映射到词表里的某个词** —— 正是"每句话都对应一个关键词"的坏处

所以正确的结论是：**要换的是模型，不是语法。**

## 为什么 4M 参数的小模型反而更准？（2026-11-16 补）

体积拆开一看就清楚了：

| | sherpa 14M | vosk small-cn |
|---|---|---|
| 神经网络 | **24.1 MB**（encoder 20.6 + decoder 1.8 + joiner 1.7），**14M 参数** | `am/final.mdl` **15.2 MB**，约 **4M 参数** |
| 语言模型 / 解码图 | **无**（greedy 解码，transducer 自带的上下文很弱） | `Gr.fst` 24.9 MB + `HCLr.fst` 15.4 MB = **40.3 MB 词图 + n-gram** |
| 说话人自适应 | 无 | `ivector/final.ie` 9.5 MB |
| 合计 | 24.1 MB | 65.1 MB |

**结论：Vosk 的神经网络比我们小 3.5 倍，它靠的是那 40MB 的解码图（词表 + n-gram 语言模型）。**

这也解释了为什么语法模式会掉点：语法模式会把 40MB 的词图**替换成我们那 18 个字的列表**——
等于把语言模型扔了，只剩声学模型在硬凑，所以 77% → 73%。

对我们的含义：

1. **M1 不需要更准**。它的职责是"筛掉长时间噪音 / 静音 / 明显在聊别的"，精度由 M2 决定。
2. 真想提准确率，杠杆在**语言模型 / 上下文偏置**，不是把声学模型换大。
   sherpa 的 streaming transducer 支持 hotwords，但这版 Node 绑定会静默忽略（已实测）——要做得换绑定或自己加。
3. **不建议升级 M1 的体积**：M1 变大只会挤压 M2 的资源预算，收益却和 M2 重复。

## 判断

**值得继续，但先不做替换。** 理由：

1. **收益明确**：同样的数据 73% vs 60%，而且"词表外输出"这一类错误被结构性地消灭了 —— 这正是我们最痛的
   （「播完了」「淡定视频」把结束词判错、把长句半句当成命令）。
2. **加载更快**（246ms），意味着**可以按需加载**、不必常驻，比 M2 更容易藏进门里。
3. **成本**：+65MB 磁盘、+105MB 内存、每段约 118ms（非流式批处理口径）。
4. **最大障碍是集成**：npm 包不可用；要用 `koffi`（我们已经在用）自己包一层 `libvosk.dll`，
   约 200 行 FFI，且需要验证流式 partial 的行为。

## FFI 集成结果（koffi，2026-11-16）

已经用 `koffi` 包好 `libvosk.dll`（`app/vosk-ffi.js`），并做成**可切换的 M1 后端**
（`settings.json` 的 `asrBackend: 'sherpa' | 'vosk'`，默认 sherpa）。

实测：

| 项 | 数值 |
|---|---|
| 模型加载（FFI） | **235 ms** |
| 30 段批测（18 字符语法） | **22/30 = 73%**（与 Python 版一致） |
| 每段耗时 | 103–117 ms |
| 流式进程就绪 | 360–370 ms |

### 又踩了两个坑（都已修）

1. **`vosk_recognizer_accept_waveform_f`（float 版）静默返回空结果** —— 不报错，但识别永远是空。
   必须转成 int16 字节、走 `vosk_recognizer_accept_waveform(char*, byteLen)`。
2. **语法字符集越大越差**：只含有录音的 6 个词（18 字符）= **73%**；
   把 21 个词（含同义词，38 字符）全带上 = **63%**。
   同义词引入的额外字符（单/站/定/淡/样/这…）会造成混淆 → 默认用"核心词"字符集（`VK_VOSK_CHARSET=core`）。

### 仍未解决

换 Vosk 后端跑端到端时，**给 M2 的确认音频有时会丢掉词头**（M2 听成「听视频」而不是「暂停视频」），
导致它按同义词「单听视频」改判 —— 动作结果相同（都是 media.toggle pause），但转写不干净。
切片逻辑（`speechAudio`）已加 400ms 间隙容忍 + 500ms 前置余量，仍偶发。下一步要么：
- 把切片改成"从上一个静音段结束处开始"（用更长的静音窗口定义句首），或
- 直接在 Vosk 侧记录"这句话开始的时间戳"，按时间切

因此 **默认后端仍是 sherpa**，Vosk 作为实验路径保留。
