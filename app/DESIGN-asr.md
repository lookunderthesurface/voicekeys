# 为什么从 KWS 换成 ASR（调研与决策记录）

> 2026-11-15。触发层原来用 sherpa-onnx 的 KWS（关键词检测），现在换成了流式 ASR + 文本匹配。
> 这份文档记录**为什么换、换了之后实测数据、以及几条性能决策**，避免以后有人（包括我）又改回去。

---

## 1. 问题：KWS 认不出用户说的话

现象：用户很认真地录了 5 段「暂停视频」，KWS 只认得出 2 段；同一批录音降到 0.01 阈值也还是 2 段。

诊断方法：拿录音逐段跑「所有已绑定关键词」的匹配，看能匹配上什么。

结果：那 5 段里 **4 段只匹配到「声音」**，没有「暂停」；后来发现用户实际说的是 **「暂停」**（两个字），而绑定的关键词是「暂停视频」（四个字）。

**根因不是阈值，是模型能力**：

- 我们的 KWS 是 `sherpa-onnx-kws-zipformer-zh-en-3M`，**3M 参数**（37MB）。
- 它的机制是把关键词拆成**固定 token 序列**（如 `b ǎ sh ēng y īn t iáo x iǎo`），声学模型逐 token 对上才触发，**没有语言模型**。
- 训练数据里没见过的说法，硬匹配也很差。官方 issue 里有人反馈 `bó` 一直被识别成 `guó`，阈值压到 0.02 也没用（[sherpa-onnx#1371](https://github.com/k2-fsa/sherpa-onnx/issues/1371)）。
- 中文调优文章直接说："不要轻易相信'任意热词免训练'的宣传，自定义热词是有限度的"（[参考](http://www.chinadongda.com/j/?weixin_30983965/article/details/166121439)）。

而用户日常用的 Handy（Whisper 类 ASR，几千万到上亿参数、带语言模型）**每次都把他说的结束词转写出来了**。这个对比很说明问题。

## 2. 业界做法：ASR 转文字，再匹配

ASR 做命令词的已知优势（[综述](https://uvadoc.uva.es/bitstream/handle/10324/84481/TFG-G8144.pdf?sequence=1)）：

| 优势 | 说明 |
|---|---|
| 词汇覆盖广 | 任何词都能识别，不需要预先"编码进模型" |
| 复用强模型 | 继承 ASR 对噪音、口音、语速的鲁棒性 |
| 加新词零成本 | 只改文本匹配表，不碰模型 |
| 准确率更高 | 有论文实测比刚性 KWS 的有效成功率高 17.4 倍（[MDPI](https://www.mdpi.com/2313-7673/11/9/670/pdf?version=1789656528)） |

代价：算力比小 KWS 高（要跑完整 ASR）。

## 3. 模型选型实测

用同一批真实录音（用户的 5 段 × 若干词）跑三个候选：

| 测试词 | KWS 3M（原方案） | 中文流式 14M | 中英双语 small |
|---|---|---|---|
| 听我说 | 5/5 | **「听我说」5/5 全对** | 「听我」×5（缺尾字） |
| 把声音调大 | 4/5 | **4/5 全对** | 未测（中文更弱） |
| 把声音调小 | 1/5 | 3/5 近对（「把声音调」） | 「把声」「把声音调」 |
| 播放视频 | 1/5 | 2/5 近对（「播放视」） | 更差 |
| over | 1/5 | ❌ 全空（纯中文） | ✅ 1/5 认出「OVER」 |

**结论**：中文场景纯中文 14M 明显最优；双语小模型为了兼顾英文，中文退化明显。
**决策**：用**纯中文 14M**，唤醒/结束词只保留中文（`听我说` / `我说完了`），**去掉英文 `over`**。

### 性能实测（14M int8，2 线程）

| 指标 | 数值 |
|---|---|
| 模型体积 | int8 三件套 **24.1 MB** |
| 加载耗时 | 553 ms |
| 解码 25 秒音频 | 329 ms 墙钟 / 1250 ms CPU → **RTF ≈ 0.05** |
| 内存 RSS | 47 MB（加载前）→ 111 MB（加载后）→ 120 MB（解码中） |

说话时约占单核 5%，对端侧完全可接受。

## 3.5 踩过的坑：ONNX Runtime 线程池会自旋

把 ASR 子进程的 `numThreads` 设成 2 以上，空闲时 CPU 会飙到 **200%（2 线程）/ 574%（4 线程）**——ORT 的 intra-op 线程池默认 spin-wait，而 14M 模型每次解码只有几毫秒，线程几乎全程在空转。

实测（实时喂静音，5 秒）：

| numThreads | CPU |
|---|---|
| 1 | **1.3%** 单核 |
| 2 | 200% |
| 4 | 574% |

**结论：这个模型必须用 `numThreads: 1`。** 多线程既没有速度收益，还会烧掉一个核。改完主进程 + ASR 子进程合计约 3.7% 单核。

## 4. CPU 绑核策略（重要，别乱改）

本机拓扑（`GetSystemCpuSetInformation` 读出的 `EfficiencyClass`）：

```
效率等级 0（E 核 / 小核）：逻辑核 6,7,8,9,10,11,12,13   ← 8 个
效率等级 1（P 核 / 大核）：逻辑核 0,1,2,3,4,5           ← 6 个
```

| 进程 | 绑核 | 原因 |
|---|---|---|
| **ASR 子进程** | 硬绑 **6 个小核**（掩码 `0x1FC0`） | 后台计算、能容忍延迟，绝不影响交互 |
| **离线分析子进程**（算阈值） | 同样绑小核 | 批处理 |
| **主进程**（麦克风采集 + 触发 + UI） | **不绑，交给系统调度** | 见下 |

**为什么主进程不绑**：Windows 官方与内核文档明确把"音频处理、摄像头采集、控制循环、接近实时的响应"列为 **EcoQoS / 降优先级要慎用**的场景。硬绑小核 + 降低调度优先级后，一旦小核被占住，音频帧就会丢——而我们的链路（100ms 一帧 → 识别 → 触发）对丢帧没有任何容错。小核单核性能约为大核的 40–60%，这个代价不值得为省几瓦电去冒。

实测亲和性设置有效：`0x3fff`（全部）→ 设成 `0x3fc0` 后读回一致。

## 5. 不做预录缓冲（pre-roll）

曾考虑"服务端常驻最近 600ms 音频，开始录制时拼接"，用来救回被吃掉的字头。

**否决原因**：那是一个常驻的滚动缓冲，违背"不额外占常驻资源"的原则；而且录制本身不是实时任务，丢那 100ms 的根因是**用户不知道什么时候才真正开始录**。

**替代方案（已采用）**：UI 上明确表示"正在准备/已开始录制"——按钮点击后先显示"正在开始…"的动画，等 HTTP 往返完成、服务端确认进入录音状态后，才切到"录音中"并开始计时。用户看到"录音中"再开口，就不会丢字头。

## 6. 匹配策略

ASR 输出常有小偏差（缺尾字、错一个字），所以不能只做精确 `includes`：

- 归一化：去掉标点与空格，英文转小写
- 命中条件（按优先级）：
  1. 文本**包含**完整关键词 → 100%
  2. 关键词的**前缀**（允许缺尾部 ≤2 字）出现在文本末尾 → 90%
  3. 编辑距离 ≤1（只在长度 ≥4 的关键词上启用）→ 80%
- 每条命中都要过"静音门"（等待 N 毫秒无人说话）与冷却时间，避免边说边触发。
